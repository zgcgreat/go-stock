## 修复：知识库问答 ResizeObserver loop 报错

**现象**：点击「知识库问答」后控制台报
`ResizeObserver loop completed with undelivered notifications`。

**根因**（SSE 流式 + MdPreview 的组合才触发）：
1. SSE 每来一个 chunk，`watch(kbqaAnswer/kbqaReasoning)` 都调
   `scrollIntoView({behavior:'smooth'})` 滚到底部；
2. `smooth` 是**异步滚动动画**，一个回答可能启动上百次，动画期间持续改变滚动位置；
3. `md-editor-v3` 内的 CodeMirror 6 挂了两个 ResizeObserver 做测量——
   `onResize`（`docView.lastUpdate < Date.now()-75` 时触发）与
   `measureSoon`（tooltip 测量），回调里**同步修改 DOM 尺寸**；
4. 两者叠加 → ResizeObserver 在同一帧被反复触发、尺寸持续变化，循环无法闭合。

**修复**（`knowledge-base-manager.vue`，commit `149f0a9`）：
- 流式期间用 `behavior:'auto'`（同步无动画），回答结束后再用 `smooth` 收尾一次
- 滚动走 rAF + cancel 前一帧 → 同一帧只滚一次；再按 120ms 节流
- `onUnmounted` 清理未执行的 rAF

**排查结论**：全站另 4 处 `scrollIntoView`（stock.vue / FundFollow.vue /
ClsCalendarTimeLine.vue / InvestCalendarTimeLine.vue）均为用户主动触发，
非高频流式且无 md-editor-v3 嵌套，不构成此问题。

**可复用经验**：
- `md-editor-v3` / CodeMirror 6 组件与「高频动画 scrollIntoView」同屏时，
  极易触发 ResizeObserver loop 报错；高频滚动一律用 `auto` 而非 `smooth`
- 高频流式场景的自动滚动三件套：rAF 合并 + 时间节流 + 卸载清理

## 修复：user-profile.vue「我的画像」采纳率 toFixed 崩溃 + Web 端信封未拆

**现象**：打开「我的画像」即报
`TypeError: Cannot read properties of undefined (reading 'toFixed')`
（user-profile.vue:49 `stats.upRate.toFixed(1)`）。

**根因**：Web 端后端（`internal/handlers/web_handler.go`）统一把数据包在
`{code,message,data}` 信封里；`services/api.js` 的响应拦截器**不拆信封**，
`wails-bridge.js` 的 Web 分支 `.then(r => r.data)` 拿到的是整个信封对象。
而 `user-profile.vue` 是按**桌面端（Wails 直接返回原始值）**约定写的：
`stats.value = res` → Web 下 `stats.upRate` 实为 `undefined` → 第 49 行崩。

**连带问题（同根因，本组件同样中招）**：`GetUserProfile`/`GetUserProfileUpdatedAt`
返回信封 → 画像文本、更新时间显示 `[object Object]`；`GetUserProfileEnabled`
`res !== false` 恒真 → 注入开关永远开；`GetConfig` 读 `res.aiConfigs`/`res.darkTheme`
为 undefined → 学习模型下拉空、深色模式恒关；`ListAgentFeedback` 读 `res.list`
为 undefined → 反馈列表空。

**修复**（commit `a738a12`，vite build 通过 EXIT=0）：在
`loadStats`/`loadFeedback`/`loadProfile`/`loadProfileEnabled`/`loadLearnModel`/
`onMounted`(GetConfig)/`relearn` 统一拆信封——`data = res.data ? res.data : res`，
并按默认值兜底（尤其 `upRate` 强制为 number）。两种模式（Web 信封 / Wails 原始值）均正确。

**注意**：`wails-bridge.js` 各函数对信封的处理**不一致**——多数只 `.then(r => r.data)`（拿信封），
唯 `GetProfileLearnAiConfigId` 写对了 `res.data?.data`。后续若有组件仍按桌面端形态消费
Web 接口，需逐个排查；根治应在桥接层统一拆 `data`（但改动面大、影响多消费者，本次未动桥接层）。

## 修复：Web 端盘前策略生成报 no such table: morning_strategies

**现象**：Web 手动生成盘前策略失败，日志
`[handlers/web_handler.go:2536] Web 手动生成盘前策略失败：保存盘前策略记录失败：
SQL logic error: no such table: morning_strategies (1)`。

**根因**：`models.MorningStrategy`（表名 `morning_strategies`）的建表 AutoMigrate
仅在**桌面端** `main.go:311` 注册；**Web 端** `internal/webserver/server.go` 的
`MigrateAllTables()` 遗漏该表，导致 Web 库从不建表，生成/查询/删除盘前策略全部失败。

**修复**（commit `4cd1957`，`go build ./web/` EXIT=0）：在 `MigrateAllTables()` 的
AutoMigrate 列表追加 `&models.MorningStrategy{}`。重启 Web 服务后 AutoMigrate 自动建表。

**排查经验**：Web 端新增/启用任意 GORM 模型时，必须**同步**检查两处迁移入口——
桌面端 `main.go` 的 `AutoMigrate()` 与 Web 端 `internal/webserver/server.go` 的
`MigrateAllTables()`，否则桌面端正常、Web 端报 no such table。本次盘前策略是 Web 二次开发
新接入的桌面端能力，移植时漏了 Web 迁移。

## 修复：晨报/复盘页「一直转圈圈」（记录卡在 generating 状态）

**现象**：打开「晨报」（morningStrategy）页永久转圈；复盘（dailyReview）页同源隐患。

**根因**：`morning_strategies` 与 `daily_reviews` 各有一条 `status='generating'` 的孤儿记录
（`strategy_date/review_date='2026-10-08'`，`updated_at≈20:10`）。生成流程中途挂掉（进程被杀/AI
调用中断），但 `GenerateMorningStrategy` 只在最终成功才把状态落为 `success`/`failed`，中断时
记录永远停在 `generating`。前端 `loadReport` 读回该记录 → `report.value.status==='generating'`
→ `isGenerating=true` → `<n-spin :show="isGenerating">` 永久显示「AI 正在生成盘前策略…」。

**关键不对称性**：`DailyReviewApi.GetDailyReviewByDate` 已有「陈旧 generating 自动复位」逻辑
（>10min 翻 failed），但 `MorningStrategyApi.GetMorningStrategyByDate` **漏了这段**；且
`MorningStrategy.vue` 的 `loadReport` **没有**在 generating 时启动 `pollStatus()`（DailyReview
同理，仅点击生成后才轮询）。所以复盘页因自愈已自愈、晨报页卡死——DB 实测印证：
`daily_reviews` 那条已被自愈翻成 failed（updated_at 20:33），`morning_strategies` 仍 generating。

**修复**（commit 待提交，`go build ./web/` + `vite build` 均 EXIT=0）：
1. `backend/agent/morning_strategy_api.go`：`GetMorningStrategyByDate` 补齐与 `daily_review_api.go`
   一致的陈旧 generating 自动复位（>10min → failed，写明确原因）。
2. `frontend/src/components/MorningStrategy.vue`：`loadReport` 读到 `generating` 时启动
   `pollStatus()`（命中真正在生成的情况，完成后自动刷新）；并补 `onUnmounted(stopPoll)` 清理
   模块级轮询定时器（原 import 了但未用，存在泄漏）。
3. `frontend/src/components/DailyReview.vue`：`loadReport` 同步补齐 generating 时 `pollStatus()`，
   与晨报对称（其后端自愈早已就位，仅前端加载路径缺口）。

**数据修复**：`data/stock.db` 中两条卡死记录已手动复位为 `failed`（immediate 解锁，不等 10min
自愈临界点）。用户重新打开晨报/复盘页即可正常显示「生成失败+原因」并可「重新生成」。

**可复用经验**：凡是有「生成中」中间态的表，读取接口必须带「陈旧 generating 自动复位」，
且前端 `loadReport` 在 generating 时要能轮询/订阅事件自动收尾，否则一次中断的生成会让页面
永久转圈。晨报/复盘是同一套模板，改动要两端同步、互为镜像。




## 修复：Web 端复盘/晨报生成时进程被 log.Fatalf 杀死（exit status 1）

**现象**：Web 端手动生成复盘报告，`exit status 1`，进程整体死亡。日志止于
`agent_api.go:498 运行预算: mode=deepagents`，2 秒后无输出。

**根因**：`internal/handlers/web_handler.go` 的 `GenerateDailyReviewHandler` /
`GenerateMorningStrategyHandler` 传 `context.Background()` → `progressEmitter`
（每 300ms 节流）→ `agent.safeEventsEmit` → `runtime.EventsEmit`。
wails v2.15 `pkg/runtime/runtime.go:getEvents()` 在 ctx 找不到 `"events"` 键时
走的是 **`log.Fatalf`（os.Exit(1)），不是 panic** —— 原 `safeEventsEmit` 的
`defer recover()` **完全无效**。名字里的 "safe" 是假的。

**修复**：新增 `backend/data/wails_events.go`
- `HasWailsEvents(ctx)`：探测 ctx 是否携带 wails 私有 `"events"` 键
- `SafeEventsEmit(ctx, event, payload)`：无该键直接返回；recover 降为第二道防线
收口 4 处调用：`agent.safeEventsEmit`、`data.EmitStockDataChanged`、
`openai_stream.go` 两处 warnMsg。移除 3 个文件里失效的 `runtime` 导入。
测试：`backend/data/wails_events_test.go`（3 个用例，含核心回归断言）。

**验证**：`go build ./backend/...` 通过；`go test ./backend/agent/` ok；
`go vet ./backend/...` 干净；`go build -o go-stock-web.exe ./web/` 成功。

**⚠️ 沉淀的通用规则**：
- wails `runtime.*` 系列函数在 ctx 非法时是 **log.Fatalf 杀进程**，绝不能靠 recover 兜底
- 任何后台任务里调 wails runtime，ctx 必须来自 Wails 生命周期钩子；Web 端一律跳过
- `main.go` 的 `initStockData/US/HK` 三处 `go runtime.EventsEmit(ctx, ...)` 同样裸调，
  当前无调用点（死代码），若将来接线需一并改 `data.SafeEventsEmit`

## 修复：AddMemory embedding 404（DeepSeek 无 /embeddings 端点）

**现象**：`AddMemory 入库失败: 写入 chunk 0/29 失败: couldn't create embedding ... 404 Not Found`，每次归档报告必现。

**根因**：用户无任何 ModelType=embedding 配置、EmbeddingModel 空、LongTermMemoryAiConfigId=0 →
`buildEmbeddingFuncWith` 自动回退选中首个可用配置（DeepSeek 官方 ID=1）→
**DeepSeek 官方 API 没有 /embeddings 端点**，text-embedding-3-small 打过去必然 404。
属配置缺失的预期降级（不影响复盘主流程），但每次归档都白发无效请求。

**修复**（`backend/agent/long_term_memory.go`）：
- 进程级熔断：`embeddingFailedCfgIDs`，AddDocument 404/401 后标记当前 aiConfig，
  后续 addMemorySync/SearchRelevant 直接跳过（429/网络错误不熔断，保留重试）
- `buildEmbeddingFuncWith` 选中已熔断配置时直接拒绝并附指引
- `resetLongTermMemoryStore`（用户切换向量服务）同步清熔断
- 指引文案明确：DeepSeek 官方无 /embeddings，需配 ModelType=embedding / EmbeddingModel
  或在知识库页指定长期记忆向量服务

**真正的解决动作在配置侧**：用户需在设置中给支持向量模型的供应商（硅基流动/OpenAI/智谱等）
配 embedding，否则长期记忆功能持续降级为文件名扫描（功能可用但无语义检索）。

测试：`long_term_memory_test.go` 5 用例（404 熔断/瞬态不熔断/reset 清除/ID解析/零ID保护）。
`go test ./backend/agent/` 全绿、vet 干净、web 二进制 21:00 重编成功。

## 功能移植：Web 端顶部快讯轮播条（对齐桌面端）

**背景**：桌面端 App.vue 顶部有 `n-marquee` 消息轮播（`telegraph` Wails 事件驱动，
Go cron 60s 直抓财联社快讯，`enableNews` 开关门控）；Web 端没有。

**方案**（纯前端，零后端改动；Web 后端 `/telegraph` 接口与 scheduler 30min 快讯入库均已就绪）：
